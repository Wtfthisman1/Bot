# Публичный доступ к боту: VPS-релей

Whisper, yt-dlp, база и файлы живут на домашней машине. VPS нужен, чтобы у
ссылок был постоянный адрес из интернета: он проксирует запросы домой через
WireGuard и **файлы у себя не хранит**.

```
пользователь ──HTTPS──> VPS (nginx) ──WireGuard──> домашняя машина (:8080)
```

Сайт — страницы входа и кабинет — отдаёт та же домашняя половина: аккаунты,
история задач и файлы лежат в её базе, и разносить это по машинам значило бы
гонять по туннелю ещё и их. Когда дом выключен, nginx показывает вместо сайта
страницу «рабочая машина спит»; бот в Telegram при этом продолжает принимать
задачи — см. [спул](#разделение-приём-на-vps-исполнение-дома).

Приём запросов можно вынести на VPS отдельно — тогда бот отвечает и при спящей
домашней машине. Как это включить, описано ниже, в разделе
«[Разделение: приём на VPS, исполнение дома](#разделение-приём-на-vps-исполнение-дома)».

Почему так, а не «заливать готовый файл на VPS»: не нужен большой диск, нет
дублей, нет рассинхрона токенов, и ссылка работает сразу, а не после заливки.
Домашний исходящий канал держит ~15 МБ/с — с запасом.

Побочный выигрыш: у nginx нет чужого лимита на размер загрузки, поэтому форма
`/upload` принимает файлы любого размера (предел задаём мы сами —
`client_max_body_size`).

## Что развёрнуто

| | |
|---|---|
| домен | `transcribot.site`, DNS на Cloudflare в режиме **DNS only** |
| VPS | Ubuntu 24.04, `REDACTED_IP` |
| туннель | WireGuard, VPS `10.8.0.1` ↔ дом `10.8.0.2` |
| наружу открыто | 22, 80, 443, 51820/udp — остальное режет ufw |
| маршруты наружу | сайт целиком; закрыты `/internal/` и `/actuator` — 404 |
| actuator | отдельный порт 8081 на `127.0.0.1`, снаружи недоступен |

**Cloudflare обязан быть в режиме DNS only (серое облако).** Включённое
проксирование (оранжевое облако) вернёт лимит в 100 МБ на бесплатном плане и
сломает отдачу больших файлов — ровно та проблема, из-за которой мы ушли с
Cloudflare-туннеля.

## Развёртывание

**1. VPS.** Скопировать на сервер и запустить:

```bash
scp deploy/vps/setup-vps.sh deploy/vps/nginx-bot.conf.template root@VPS_IP:/root/
ssh root@VPS_IP "DOMAIN=transcribot.site HOME_PUBKEY=<публичный ключ дома> bash /root/setup-vps.sh"
```

Скрипт идемпотентный — гонять можно сколько угодно, ключи не перегенерируются.
Если домен ещё не резолвится в этот сервер, он доходит до сертификата и
останавливается: Let's Encrypt проверяет владение через DNS, без него шаг
бессмысленен. Почините DNS и запустите повторно — продолжит с этого места.

В конце печатает публичный ключ VPS — он нужен для следующего шага.

**2. Домашняя машина.**

```bash
sudo VPS_PUBKEY=<ключ из шага 1> VPS_IP=REDACTED_IP bash deploy/home/setup-home.sh
```

Приватный ключ берётся из `~/.vps-transcribot/wg-home.key` и наружу не уезжает.
Скрипт сам проверяет связь: в конце должно быть «10.8.0.1 отвечает».

**3. Бот.** В `.env`:

```
UPLOAD_BASE_URL=https://transcribot.site
DOWNLOAD_BASE_URL=https://transcribot.site
```

## Проверка

С устройства **вне** домашней сети (телефон по мобильному интернету):

```bash
curl -I https://transcribot.site/download/<токен из сообщения бота>
```

Ожидается `200`, `content-type: video/mp4` и `content-disposition`.
`/actuator` снаружи обязан давать `404`, `/internal/home/status` — тоже.

Проверить всю цепочку, не имея живого токена, можно и так — ответы приходят
от бота через туннель:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://transcribot.site/                        # 200 (сайт)
curl -s -o /dev/null -w "%{http_code}\n" https://transcribot.site/download/bogus          # 404
curl -s -o /dev/null -w "%{http_code}\n" https://transcribot.site/actuator/health         # 404
curl -s -o /dev/null -w "%{http_code}\n" https://transcribot.site/internal/home/status    # 404
```

## Разделение: приём на VPS, исполнение дома

По умолчанию обе половины поднимаются в одном процессе дома, и VPS остаётся
чистым релеем. Разделение переносит на сервер только приём запросов:

```
Telegram ──> VPS (бот) ──WireGuard──> дом: очередь, база, Whisper, файлы
                  ▲                            │
пользователь ─────┘ (nginx: /download, /upload)┘
```

Что это даёт: бот отвечает всегда, даже когда домашняя машина выключена, — и
задачу при этом принимает. Присланное при спящем доме ложится в спул на диске
VPS (`/opt/transcribot/spool`, файл на задачу) и уходит в работу при первом же
успешном обращении; пользователю говорят «принято, начнётся, когда машина
проснётся», а потом — «машина проснулась, задачи пошли в работу».

Чего спул не умеет: выдать ссылку на форму загрузки и прислать готовую
расшифровку. Форму отдаёт дом, файлы лежат у него — на эти действия при спящей
машине приходит «недоступно».

База на VPS не поднимается сознательно: там 960 МБ памяти, и Postgres рядом
со Spring не оставит запаса. Спулу база не нужна — десяток JSON-файлов.

**1. Общий ключ.** Внутренние адреса дома (`/internal/**`) закрыты общим
ключом — туннеля мало, в домашней сети есть и другие машины. Сгенерируйте:

```bash
openssl rand -base64 32
```

Положите его в `.env` дома (`HOME_API_KEY=...`) и передайте на VPS шагом 2.

**2. Служба на VPS.**

```bash
scp deploy/vps/setup-bot.sh deploy/vps/transcribot-bot.service root@VPS_IP:/root/
ssh root@VPS_IP "BOT_TOKEN=<токен> ADMIN_CHAT_ID=<id> HOME_API_KEY=<ключ> bash /root/setup-bot.sh"
```

Скрипт ставит headless JRE, заводит пользователя `transcribot`, кладёт секреты
в `/etc/transcribot/bot.env` (640, читает только служба) и включает юнит.
Повторный запуск обновляет юнит и **не трогает уже записанные секреты**.

**3. Jar.** Собирается дома — на 960 МБ памяти собирать нечем:

```bash
./gradlew bootJar
~/.vps-transcribot/put.py build/libs/bot.jar /opt/transcribot/bot.jar
echo 'systemctl restart transcribot-bot' | ~/.vps-transcribot/rsh.py
```

**3.5. Промежуточная проверка.** Перед переключением стоит убедиться, что путь
до дома вообще работает, — на этом шаге бот ещё отвечает как обычно:

```bash
# дом уже с новым jar и ключом в .env
sudo systemctl restart transcribot

# с VPS: без ключа 403, с ключом — сводка задач
echo 'curl -s -o /dev/null -w "%{http_code}\n" \
  "http://10.8.0.2:8080/internal/home/status?ownerType=TELEGRAM&ownerId=1"' \
  | ~/.vps-transcribot/rsh.py
```

403 здесь — правильный ответ: фильтр на месте. Если приходит 000 или таймаут,
дело в туннеле или в том, что дом не слушает 8080, — переключаться рано.

**4. Дом перестаёт принимать апдейты.** Профиль задаётся drop-in-файлом: правка
самого юнита разошлась бы с репозиторием, а так откат — это `rm` одного файла.

```bash
sudo mkdir -p /etc/systemd/system/transcribot.service.d
printf '[Service]\nEnvironment=SPRING_PROFILES_ACTIVE=home\n' \
  | sudo tee /etc/systemd/system/transcribot.service.d/profile.conf
sudo systemctl daemon-reload && sudo systemctl restart transcribot
```

Вернуть всё домой, если понадобится:

```bash
sudo rm /etc/systemd/system/transcribot.service.d/profile.conf
sudo systemctl daemon-reload && sudo systemctl restart transcribot
```

Это обязательный шаг: `getUpdates` Telegram отдаёт одному процессу, два long
polling начнут отбирать апдейты друг у друга — в логах пойдут `409 Conflict`,
а сообщения будут теряться через раз.

**5. Порт 8080 дома — файрвол не трогаем.** Внутренний API закрыт ключом
`X-Home-Key`: без него любой запрос получает 403, снаружи дом и так за NAT
роутера. Наружу открыт только VPS — 22, 80, 443, 51820/udp.

> **ufw на домашней машине включать нельзя.** Весь её трафик идёт через
> TUN-клиент sing-box, и ответные пакеты приходят в `tun0` как **входящие**.
> `ufw enable` ставит политику «входящие — DROP» и рубит вместе с ними DNS:
> ping по IP живёт, а сайты не открываются. Проверено 2026-08-26.

Если захочется закрыть 8080 от локальной сети, это делается не файрволом, а
привязкой сокета: `server.address=10.8.0.2` в профиле `home`. Тогда служба
станет зависеть от поднятого `wg0` — добавить в юнит `After=wg-quick@wg0`.

### Проверка

```bash
# бот жив и знает адрес дома
echo 'journalctl -u transcribot-bot -n 20 --no-pager' | ~/.vps-transcribot/rsh.py

# внутренний API дома не пускает без ключа (ожидается 403)
echo 'curl -s -o /dev/null -w "%{http_code}\n" http://10.8.0.2:8080/internal/home/status' \
  | ~/.vps-transcribot/rsh.py
```

В самом Telegram: `/status` должен ответить сводкой (значит, VPS достучался до
дома). При выключенной домашней машине присланная ссылка принимается с
пометкой «начнётся, когда машина проснётся», а `/status` считает её в
ожидающих. Что лежит в спуле, видно и снаружи:

```bash
echo 'ls -1 /opt/transcribot/spool | wc -l' | ~/.vps-transcribot/rsh.py
```

## Сайт: аккаунты, история и квота

Сайт отдаёт домашняя половина — та же, что считает Whisper. Аккаунты, задачи и
файлы лежат в её базе, поэтому страницы стоят рядом с данными, а не за туннелем
от них. Наружу их пускает тот же nginx: `location /` теперь проксирует домой,
а `/internal/` и `/actuator` закрыты явными правилами.

```
пользователь ─HTTPS─> VPS (nginx) ─WireGuard─> дом: сайт, база, очередь, файлы
Telegram ───────────> VPS (бот) ──WireGuard──> дом: та же очередь
```

**Что на сайте есть.** Регистрация и вход — почта с паролем, Telegram, Google;
кабинет с историей задач, постановка задачи ссылкой и загрузка файла, выдача
результата во всех форматах — текст, SRT, VTT, Word, — и счётчик оставшихся
расшифровок.

### Один человек — один аккаунт

Задачи по-прежнему записаны на владельца: чат в Telegram или аккаунт сайта.
Иначе результат из чата некуда было бы отправить. Но считаются они по аккаунту:

* вход через Telegram ищет аккаунт по тому же идентификатору, которым бот
  подписывает задачи из переписки, — история из чата видна в кабинете сразу,
  привязывать ничего не нужно;
* если человек сначала завёл аккаунт по почте, а потом пришёл в бота (или
  наоборот), в кабинете есть кнопка «Получить код привязки». Код присылается
  боту командой `/link КОД`, и переписка переезжает в этот аккаунт;
* чат, который нигде не регистрировался, получает свой аккаунт молча при первой
  же задаче — иначе он обходил бы лимит просто потому, что пришёл раньше сайта.

### Квота

Три бесплатные расшифровки в календарный месяц на аккаунт. Скачивание файлов в
лимит не входит: видеокарта на нём не работает. Сорвавшиеся задачи не
считаются.

Считает всегда дом — только у него есть база. Бот на VPS получает готовый ответ
«принято» / «отложено» / «лимит исчерпан» и пересказывает его человеку; задача
из спула, для которой лимит кончился, пока она лежала, снимается с объяснением,
а не молча.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `QUOTA_ENABLED` | `true` | `false` — лимита нет вовсе |
| `QUOTA_FREE_PER_MONTH` | `3` | сколько расшифровок в месяц |
| `QUOTA_ZONE` | `Europe/Moscow` | по какому поясу начинается месяц |

### Вход через Telegram

Способов два, и они не дублируют друг друга.

**Виджет Telegram.** Спрашивает номер телефона и присылает подтверждение в
приложение. Виджету нужен домен, привязанный к боту, иначе кнопка молча не
работает: в [@BotFather](https://t.me/BotFather) `/setdomain` → выбрать бота →
`transcribot.site`. Ключей и секретов нет — подпись проверяется токеном бота,
который у дома уже есть.

**Вход через бота, без номера.** Сайт выдаёт одноразовый код, открывает
`t.me/<бот>?start=login_<код>`, и бот спрашивает подтверждение кнопкой.
Страница ожидания обновляет себя каждые три секунды (`meta refresh`, без
JavaScript) и уходит в кабинет, как только подтверждение придёт.

Подтверждение именно кнопкой, а не самим переходом по ссылке: ссылку можно
прислать постороннему, и тогда его нажатие «Запустить» пустило бы отправителя
в чужой аккаунт. В тексте кнопки назван домен, рядом есть «Это не я», код
живёт пять минут и срабатывает один раз. Войти при этом может только тот
браузер, который вход начал: код лежит в его сессии.

Оба способа ищут аккаунт по одному и тому же идентификатору Telegram, так что
приводят в одну учётную запись — и в ту же, где лежат задачи из переписки.

### Вход через Google

Нужны ключи приложения. В [Google Cloud Console](https://console.cloud.google.com/)
→ APIs & Services → Credentials → Create credentials → OAuth client ID → Web
application, и в «Authorized redirect URIs» вписать:

```
https://transcribot.site/login/oauth2/code/google
```

Дальше в `.env` домашней машины:

```
GOOGLE_CLIENT_ID=...apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=...
```

Пустые значения означают «входа через Google нет» — кнопка просто не
показывается, и дом поднимается как обычно.

### Что дописать в `.env` дома

```
# Куку сессии наружу отдаём только по HTTPS — а снаружи всё идёт через nginx
SESSION_COOKIE_SECURE=true
```

Без этой строки вход работает, но кука уходит и по http. Локальной разработке
она мешает, поэтому по умолчанию выключена.

### Проверка сайта

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://transcribot.site/login    # 200
curl -s -o /dev/null -w "%{http_code}\n" https://transcribot.site/cabinet  # 302 на /login
```

Дальше руками: зарегистрироваться, поставить задачу ссылкой, дождаться её в
истории, скачать текст. Затем `/link` в боте — и задачи из переписки должны
появиться в той же истории, а счётчик квоты — стать общим.

### Чего на сайте нет

Регистрации по номеру телефона — решено не делать: отправить код неоткуда,
а SMS-шлюз это отдельная платная услуга. Входов три: почта с паролем, Telegram
и Google.

## Если что-то не работает

| Симптом | Куда смотреть |
|---|---|
| домен не резолвится | `curl 'https://dns.google/resolve?name=transcribot.site&type=A'` |
| туннель молчит | `wg show wg0` с обеих сторон, `journalctl -u wg-quick@wg0` |
| nginx отдаёт 502 | бот не запущен либо не слушает `0.0.0.0:8080` |
| скачивание рвётся на середине | таймауты в конфиге nginx (`proxy_read_timeout`) |
| сертификат не продлился | `systemctl status certbot.timer`, `certbot renew --dry-run` |
| бот на VPS молчит | `journalctl -u transcribot-bot -f`; чаще всего не задан `HOME_API_URL` или не совпал ключ |
| в логах 409 Conflict | апдейты читают оба процесса — дома не включён профиль `home` (шаг 4) |
| дом отвечает 403 на `/internal/` | `HOME_API_KEY` разный с двух сторон либо пуст дома |
| рукопожатия идут, а дом не отвечает | адрес слетел с `wg0` — проверить `ip -br a show wg0`. NetworkManager считает `wg0` своим и снимает адрес по клику в апплете; лечится файлом `/etc/NetworkManager/conf.d/99-unmanage-wg0.conf` с `unmanaged-devices=interface-name:wg0` |
| дома пропал интернет после `ufw` | `sudo ufw disable` — см. шаг 5, ufw дома включать нельзя |
| вместо сайта «рабочая машина спит» | так и есть: дом выключен. Проверить `wg show wg0` и что служба дома запущена |
| кнопка входа Telegram ничего не делает | в BotFather не задан домен: `/setdomain` → `transcribot.site` |
| после Google возвращает на внутренний адрес | не применился `server.forward-headers-strategy=framework` либо nginx не шлёт `X-Forwarded-Proto` |
| вход слетает при каждом переходе | `SESSION_COOKIE_SECURE=true` при работе по http — кука не сохраняется |
| «лимит исчерпан» на первой же задаче | задачи чата и аккаунта считаются вместе — посмотреть историю в кабинете; выключается `QUOTA_ENABLED=false` |
| спул не разбирается | `journalctl -u transcribot-bot | grep спул`; каталог должен принадлежать пользователю `transcribot` |
